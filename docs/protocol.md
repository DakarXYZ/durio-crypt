# Протокол Stoat поверх Olm/Megolm: отличия от Matrix

Для внутреннего ревью (CR-16). Криптография — `matrix-sdk-crypto` 0.19.1 / vodozemac без изменений; ниже —
только то, чем dur.io отличается от Matrix CS API и почему. Контракт v1 — `fixtures/`.

## Транспорт и идентификаторы

- Пути свои (`/e2ee/keys/*`, `/e2ee/to_device`, `/e2ee/backup/*`, `/e2ee/secrets/*`), тела — форма Matrix
  (C1). Синхронизации (`/sync`) нет: события приходят по WebSocket (`E2eeToDevice`, `E2eeDeviceListUpdate`,
  `E2eeKeysLow`), ящик to_device — `GET ?limit` + `POST ack {ids}` (C2), дубли отбрасываются по множеству
  обработанных id, которое коммитится вместе с изменениями хранилища.
- `user_id = @{lower(ulid)}:stoat.invalid`, `room_id = !{lower(channel)}:stoat.invalid`, `device_id` = ULID
  сессии (C15). Домена нет — сервер один на аккаунт; на клиенте машина на каждую пару (аккаунт, сервер).
- `keys/changes` нет: после переподключения все отслеживаемые пользователи перечитываются (Q10). Вход/выход
  участника группы не публикует изменение списка устройств — клиент сам перечитывает ключи и ротирует.
- `PUT /to_device` может вернуть `failed` (ящик получателя полон) — повторы с паузой и отчёт в UI.

## Сообщения

- Конверт v1 строгий: `{v, algorithm, session_id, device_id, ciphertext}`; `sender_key` не передаётся,
  `device_id` — подсказка, сверяется с владельцем сессии.
- Открытый текст Megolm — `{"type":"stoat.message","room_id",content: payload v1}`; payload несёт
  `client_nonce`, `edit_of`/`edit_seq`, `in_reply_to`, `ts`, паддинг до 256 байт (C7, Q9).
- **Своя привязка к контексту (CR-19)**, которой в Matrix нет: таблица (session, index) → message_id
  (повтор под другим id), монотонный `edit_seq` (откат правки), сверка `in_reply_to` с открытыми
  `replies` **как множеств** (бэкенд убирает повторы id, порядок не значим; лишний или пропавший id —
  `reply_mismatch`). Клиент кладёт в `in_reply_to` ровно те id, что шлёт в `replies` с
  `fail_if_not_exists: true` (иначе бэкенд молча выбросит удалённое сообщение). Сервер ничего не проверяет:
  всё внутри шифротекста.
- Каналы гильдий не шифруются; шифруются ЛС и группы. Упоминания, embeds, поиск, текст push для
  зашифрованных сообщений сервер не видит и не делает.

## Доверие

- Кросс-подписания нет до v1.1: доверие — локальное, на устройство, после SAS. Щит: `Verified`,
  `Unverified`, `UnknownDevice`, `Unauthenticated` (ключ из бэкапа/пересылки), `Mismatch`.
- Запросы ключей (`m.room_key_request`) шлёт ядро, а не библиотека: с паузой 3 с и только при своём
  проверенном устройстве; отвечают только свои проверенные устройства.
- SAS только через to_device (без комнатной верификации), только `m.sas.v1`, эмодзи и числа.

## Бэкап и восстановление

- Алгоритм бэкапа — `m.megolm_backup.v1.curve25519-aes-sha2` (Q22), `auth_data.signatures = {}`; версия — в
  query (`?version=`), `etag` — строка. Создание новой версии поверх существующей, удаление версии и секреты
  кросс-подписания требуют MFA-тикета (`x-mfa-ticket`) — в Matrix этого нет (Q13).
- Секретное хранилище — `/e2ee/secrets/<type>` вместо account data: белый список имён, ≤ 32 записей,
  ≤ 16 КиБ. Формат — `m.secret_storage.v1.aes-hmac-sha2`, `m.secret_storage.default_key`,
  `m.megolm_backup.v1` как в Matrix.
- **Ключ восстановления = ключ секретного хранилища** (base58, 48 символов), ключ бэкапа лежит в
  `m.megolm_backup.v1`. Пароль (опционально) — `m.pbkdf2`. Ротация бэкапа не меняет ключ восстановления.
- Клиент не переходит на новую версию бэкапа, созданную другим устройством, пока пользователь не введёт
  ключ восстановления (409 → загрузка остановлена).

## Вложения

- `EncryptedFile` v2 без поля `url` (id файла autumn — в `Attachment.id`), миниатюра — отдельный файл с
  отдельным ключом (C8). id миниатюр перечисляются в открытом `attachments` сообщения, иначе сервер удалит
  их через час (C9). Голосовые — обычный JSON в `content`, поля `voice` нет.
- Расшифровка строго после проверки SHA-256 всего шифротекста (в Matrix — рекомендация, у нас — тип API).
