# ADR 0001. Крипто-ядро: matrix-sdk-crypto за тонким адаптером

- Статус: **принято** (по итогам спайка CR-01), 2026-10-17
- Контекст плана: `docs/plan/20-crypto-core.md` (CR-01), `00-architecture.md` (R2, R5, §3, §4), `95-review.md`
  (C1, C2, C7, C8, C15, Q1, Q6), решение владельца O4.
- Доказательства: `docs/spike-report.md`, тесты `spikes/spike-msc/tests/*`, фикстуры `fixtures/`.

## Решение

Ядро `stoat-crypto` строится на **`matrix-sdk-crypto` 0.19.1** (`OlmMachine`) + **`matrix-sdk-sqlite` 0.19.1**
(Android) / **`matrix-sdk-indexeddb` 0.19.1** (for-web в Electron) за нашим тонким API (эскиз из
20-crypto-core). Своим кодом остаются: адаптер (CR-20), привязка payload к контексту и replay (CR-19),
вычисление щита доверия, FFI/wasm-обёртки. Свой слой на vodozemac **не пишем**; vodozemac напрямую используется
только в тестах (оракул/разбор шифротекста).

## Сопутствующие решения

- **Алгоритм бэкапа — `m.megolm_backup.v1.curve25519-aes-sha2`** (Q22). Ключи из бэкапа и пересланные ключи в UI —
  «автор не подтверждён» (`Unauthenticated`, `s03`, `s06`). `auth_data.signatures` пустой (кросс-подписания нет).
  `stoat.backup.v1.aead` не реализуем; BE-08 может держать его в белом списке на будущее.
- **Recovery key** — формат Matrix (base58, 48 символов, группы по 4), `BackupDecryptionKey`.
- **Рантайм — tokio** (C24): `matrix-sdk-sqlite` работает на `deadpool`/tokio; для UniFFI —
  `async_runtime = "tokio"`, один общий рантайм ядра. В wasm — `wasm-bindgen-futures`.
- **Доверие v1** — устройство, без кросс-подписания: `TrustRequirement::Untrusted`, `CollectStrategy::AllDevices`;
  «проверено» = локальное доверие после SAS (`Device::is_verified()`), считает адаптер (библиотека без
  кросс-подписания показывает всех как `UnsignedDevice`). Режим MSC4153 («только подписанные») — v1.1 вместе с
  кросс-подписанием.
- **Ящик to_device (C2)** — множество обработанных-но-не-подтверждённых id сериализуется в `next_batch_token` и
  коммитится **в той же транзакции**, что и изменения крипто-хранилища; события подаются в `receive_sync_changes`
  **по одному** в порядке сервера. Дубли отбрасываются до библиотеки (S12). Библиотека и сама распознаёт повтор
  Olm по хешу (`ReplayedMessage`) — наш фильтр остаётся страховкой.
- **Replay/правки/ответы (CR-19)** — наш слой: `(session_id, message_index) → message_id` (индекс берём из
  шифротекста `MegolmMessage::message_index`), монотонный `edit_seq`, сверка `in_reply_to` с `replies`. В
  matrix-sdk-crypto проверки повтора Megolm нет — подтверждено.
- **Подпись запросов/ответов** — JSON-строки на границе FFI; ответы сервера разбираются
  `IncomingResponseExt::try_from_http_response` (как в `matrix-sdk-crypto-ffi`). ruma-типы наружу не торчат.
- **Тулчейн** — `rust-toolchain.toml` = 1.96.1 (MSRV 0.19.1 = 1.96).
- **Контракт v1** (JSON `/e2ee/*` в форме Matrix, конверт v1, payload v1, события WS) — черновик заморозки в
  `fixtures/` (сгенерирован прототипом). Отличия от плана, о которых должен знать бэкенд, — отчёт §5.

## Обязательные правила адаптера (выявлены спайком)

1. Подавать to_device по одному событию (иначе запрос ключа, пришедший в одной пачке с ключом, теряется).
2. После каждого прохода — `get_missing_sessions(∅)` (ответы на запросы ключей, залечивание Olm).
3. Держать в `tracked_users` себя и всех участников зашифрованных каналов (иначе запросы SAS игнорируются, а
   отправитель не связывается с устройством).
4. Не пересылать `sender_key` в конверт; `device_id` в конверте — подсказка, сверяется с
   `EncryptionInfo.sender_device` (несовпадение → `Mismatch`).
5. Сериализовать операции на один аккаунт (актор, CR-17) и держать файловый замок на хранилище — библиотека не
   защищает от второго экземпляра.

## Дополнения (блок 3B, 2026-10-18)

### A1. Таблицы CR-19: хранение и обрезка

Решение по открытому вопросу отчёта §6 («таблица replay — своя таблица или `custom_value`»): **`custom_value`
хранилища библиотеки**, своей SQLite-таблицы нет (второй файл/соединение, отдельная миграция и отдельная
реализация для IndexedDB не окупаются). Значения шифруются `StoreCipher`, как всё хранилище, и переживают рестарт.
Ключи (`crates/stoat-crypto/src/binding.rs`):

| Ключ | Что | Граница |
| --- | --- | --- |
| `stoat.seen.v1.<session_id>` | канал сессии + `message_index → message_id` | 1024 индекса на сессию (уходят младшие) |
| `stoat.seen.v1` | порядок появления сессий | 2048 сессий (уходят старейшие вместе с их записью) |
| `stoat.edits.v1.<channel>` | только правленые сообщения: `message_id → (edit_seq, session, index)` показанной версии | 512 на канал (уходят старейшие ULID) |

Сессии ротируются раз в 100 сообщений/неделю, поэтому запись сессии мала: расшифровка = одно чтение и одна запись
только при первом показе индекса. Цена границ: повтор (session, index) из вытесненной сессии и откат правки
вытесненного сообщения больше не помечаются. Первый увиденный устройством `message_id` для (session, index)
считается оригиналом — если сервер первой отдаст копию, помечен будет оригинал. Ключи блока 3A
(`stoat.replay.*`, `stoat.edit.*`) не мигрируются: сборки с ними не выпускались.

**Правки.** Правка в Stoat — `PATCH` на месте, id сообщения не меняется, поэтому `edit_of` обязан равняться id
сообщения, которое его несёт. `edit_mismatch` = (`edit_of` ≠ id) или поля несогласованы (`edit_of` без
`edit_seq ≥ 1` и наоборот). `stale_edit` — версия с `edit_seq` не выше уже показанной (кроме перерасшифровки той
же версии).

### A2. Запросы ключей (CR-08)

Автоматические `m.room_key_request` библиотеки выключены (`set_room_key_requests_enabled(false)`); ядро зовёт
`request_room_key` само: через `key_request_delay_ms` (3 с) после первой неудачи, если ключ так и не пришёл, есть
хотя бы одно своё **проверенное** устройство и ключ не отозван (`withheld`). Пришедший напрямую ключ гасит
ожидание, а уже ушедший запрос отменяется `request_cancellation` (пересланный ключ отменяет сама библиотека).
Сессия, известная в другом канале (свой канал по таблице A1 или входящая сессия любого известного канала), — это
перенос сервером (отчёт §5.6): ошибка `ChannelMismatch`, запрос не шлётся. Состояние в памяти: после рестарта
клиент перерасшифровывает ожидающие сообщения, и они встают в очередь заново. Коды `m.room_key.withheld` →
`DecryptError::Withheld(WithheldReason)`; для UI — `DecryptError::kind()`.

### A3. Исходящие запросы: стабильные id, лимиты сервера, полный ящик

- `OlmMachine::outgoing_requests` при каждом вызове «забывает» key query в полёте (их ответ не снимает dirty) и даёт
  загрузке ключей новый id. Ядро кэширует запросы библиотеки и обновляет кэш только после изменений и не при key
  query в полёте (кроме `prepare_send`/`encrypt`, которым нужны свежие ключи участников, и запроса старше 60 с);
  загрузка с тем же телом сохраняет id. Хост держит множество id в полёте (контракт — документация крейта).
- Тела режутся по `max_to_device_batch`/`max_request_bytes` из `GET /` (`set_server_limits`), claim — по 256
  устройств; запрос библиотеки отмечается, когда отмечены все части; ответы частей claim склеиваются.
- `failed` в ответе `PUT /to_device` (полный ящик): тот же контент отказанным устройствам с новым `txn_id`, пауза
  1, 2, 4… мин, 8 попыток (`Timing`), очередь — в `custom_value` (`stoat.outbox.retries.v1`, ≤ 256). После
  последней попытки устройство попадает в `undelivered_devices()` (UI) до первой успешной доставки ему.
- Состав канала (`set_channel_members`): любое изменение — все участники `dirty` (бэкенд не шлёт
  `E2eeDeviceListUpdate` на join/leave), выход участника — сброс исходящей сессии (ротация на следующей отправке),
  вход — без ротации.

## Дополнения (блок 3C, 2026-10-18)

### A4. Вложения, SAS, бэкап

- **Вложения (CR-10)** — свой чанковый `AttachmentEncryptor`/`AttachmentVerifier`/`AttachmentDecryptor` на
  RustCrypto (те же версии `aes`/`ctr`/`sha2`, что у библиотеки), а не `Read`-обёртки библиотеки: те
  сравнивают хеш не за константное время и отдают открытый текст до проверки. Формат проверен с реализацией
  библиотеки в обе стороны. Расшифровка — только после `AttachmentVerifier::finish()` (тип API).
- **SAS (CR-11)** — `VerificationRequest`/`Sas` библиотеки за `SasHandle` и плоским `SasState`. Сообщения
  от действий пользователя идут через outbox (свои запросы), ответы библиотеки — через её
  `outgoing_requests`. Последнее состояние потока хранится у нас (≤ 64 потоков): библиотека забывает
  завершённые потоки при сборке мусора. Таймауты — библиотечные (запрос 10 мин, SAS 5 мин / 1 мин на шаг);
  сборка мусора идёт в `receive_sync_changes`, поэтому при открытом потоке `outgoing_requests` делает пустой
  проход, а `wakeup_in_ms` ≤ 10 с. `start` другой стороны внутри принятого запроса принимается
  автоматически.
- **Ключ восстановления (CR-12) — ключ секретного хранилища**, а не `BackupDecryptionKey`, как было записано
  после спайка: ключ бэкапа случаен и лежит в секрете `m.megolm_backup.v1`, зашифрованный ключом хранилища
  (`m.secret_storage.v1.aes-hmac-sha2`). Так ротация бэкапа не меняет то, что пользователь записал, а пароль
  (`m.pbkdf2`) работает наравне с ключом. Формат строки тот же (base58, 48 символов).
- **Настройка бэкапа** — `POST /backup/version` первым (с MFA-тикетом, если версия есть), затем секреты:
  секреты не перезаписываются, пока сервер не принял новую версию. Неподтверждённые `PUT /secrets/*` хранятся
  в `stoat.secrets.pending.v1` и уходят после рестарта. Состояние бэкапа — `stoat.backup.v1` (библиотека не
  помнит «включён» между запусками), ключ хранилища — `stoat.recovery.v1`.
- **Чужая версия** (404/409 при загрузке) — загрузка остановлена (`BackupVersionChanged`), включается снова
  только после `unlock_backup` с ключом восстановления; версия с публичным ключом, не совпадающим с ключом из
  секрета, отвергается (`BackupKeyMismatch`).
- Чек-лист ревью и принятые ослабления — `docs/security-review.md`; отличия протокола — `docs/protocol.md`.

## Дополнения (блок 3D, 2026-10-18)

### A5. FFI (CR-13) и стенд (CR-15)

- **Рантайм.** `#[uniffi::export(async_runtime = "tokio")]` не используется: каждый async-экспорт
  `stoat-crypto-ffi` кладёт работу задачей на **один** многопоточный tokio-рантайм процесса (2 воркера + пул
  блокирующих для SQLite), Kotlin ждёт `JoinHandle`. Паника в задаче → `CryptoException.Panic`, отмена корутины
  не останавливает операцию (она дописывает результат). Синхронные экспорты — `catch_unwind` внутри контекста
  рантайма. Объекты, держащие машину, освобождаются в контексте рантайма (`InRuntime`): `Drop` пула
  `matrix-sdk-sqlite` требует tokio.
- **Форма API.** Тела запросов/ответов, payload, конверт и `EncryptedFile` — JSON-строки; всё, по чему ветвится
  UI (`RequestKind`, `DecryptResult`, `SasState`, ошибки), — типы. Ошибка расшифровки — значение
  (`DecryptResult.Failed`). Kotlin-пакет `uniffi.stoat_crypto`, `android_cleaner = false` (minSdk 26).
- **Размер.** Профиль `release-android` (`opt-level = "s"`): arm64 10,09 МБ stripped / 3,77 МБ gzip, порог CI
  +5 % (`scripts/check-so-size.sh`), выравнивание `LOAD` 16 КБ у 64-битных ABI. Вдвое больше пробы CR-01: проба
  не затрагивала SAS/бэкап/секреты, а `panic = "unwind"` сохраняет таблицы раскрутки.
- **Стенд.** `stoat-crypto-testkit` — сценарии `#[ignore]` против живого бэкенда (delta + bonfire + autumn в
  Docker, `scripts/testkit-backend.sh`); лимиты запросов бэкенда не отключаются (выключателя нет, кроме
  `TEST_DB`, который меняет базу), клиент выжидает 429.

## Дополнения (блок 5A, 2026-10-18)

### A6. Экспорт ключей в файл (CR-21)

- Формат — Matrix «Megolm session export» библиотеки (`encrypt_room_key_export` / `decrypt_room_key_export`:
  PBKDF2-SHA-512 → AES-256-CTR + HMAC-SHA-256), своего AEAD нет. Экспорт — 500 000 раундов; файл читают и
  другие Matrix-клиенты, из чужого файла импортируются только сессии каналов Stoat (`!…:stoat.invalid`).
- Перед библиотекой ядро проверяет заголовок файла (`export.rs::check_header`): версия 1, длина не меньше
  формата, раунды PBKDF2 из файла — 1…1 000 000 (как для пароля бэкапа), иначе `InvalidKeyFile`. Иначе файл
  заставил бы устройство считать часами, а слишком короткий файл с верным MAC дошёл бы до среза в библиотеке.
- Импорт — `import_room_keys(keys, None)`: сессии `imported` → щит `Unauthenticated`; существующая сессия не
  ухудшается (слияние библиотеки). Пришедшие ключи гасят ожидающие запросы (CR-08), как ключи из ящика.
  Неверный пароль и изменённый файл неразличимы (`WrongPassphrase`, MAC).
