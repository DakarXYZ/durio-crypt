# ADR 0001. Крипто-ядро: matrix-sdk-crypto за тонким адаптером

- Статус: **принято** (по итогам спайка CR-01), 2026-10-17
- Контекст плана: `docs/plan/20-crypto-core.md` (CR-01), `00-architecture.md` (R2, R5, §3, §4), `95-review.md`
  (C1, C2, C7, C8, C15, Q1, Q6), решение владельца O4.
- Доказательства: `docs/spike-report.md`, тесты `spikes/spike-msc/tests/*`, фикстуры `fixtures/`.

## Решение

Ядро `stoat-crypto` строится на **`matrix-sdk-crypto` 0.19.1** (`OlmMachine`) + **`matrix-sdk-sqlite` 0.19.1**
(Android) / **`matrix-sdk-indexeddb` 0.19.1** (for-web в Electron) за нашим тонким API (эскиз из
20-crypto-core). Своим кодом остаются: адаптер (CR-20), привязка payload к контексту и replay (CR-19),
вычисление щита доверия, FFI/wasm-обёртки. Свой слой на vodozemac **не пишем**; vodozemac напрямую используется
только в тестах (оракул/разбор шифротекста).

## Сопутствующие решения

- **Алгоритм бэкапа — `m.megolm_backup.v1.curve25519-aes-sha2`** (Q22). Ключи из бэкапа и пересланные ключи в UI —
  «автор не подтверждён» (`Unauthenticated`, `s03`, `s06`). `auth_data.signatures` пустой (кросс-подписания нет).
  `stoat.backup.v1.aead` не реализуем; BE-08 может держать его в белом списке на будущее.
- **Recovery key** — формат Matrix (base58, 48 символов, группы по 4), `BackupDecryptionKey`.
- **Рантайм — tokio** (C24): `matrix-sdk-sqlite` работает на `deadpool`/tokio; для UniFFI —
  `async_runtime = "tokio"`, один общий рантайм ядра. В wasm — `wasm-bindgen-futures`.
- **Доверие v1** — устройство, без кросс-подписания: `TrustRequirement::Untrusted`, `CollectStrategy::AllDevices`;
  «проверено» = локальное доверие после SAS (`Device::is_verified()`), считает адаптер (библиотека без
  кросс-подписания показывает всех как `UnsignedDevice`). Режим MSC4153 («только подписанные») — v1.1 вместе с
  кросс-подписанием.
- **Ящик to_device (C2)** — множество обработанных-но-не-подтверждённых id сериализуется в `next_batch_token` и
  коммитится **в той же транзакции**, что и изменения крипто-хранилища; события подаются в `receive_sync_changes`
  **по одному** в порядке сервера. Дубли отбрасываются до библиотеки (S12). Библиотека и сама распознаёт повтор
  Olm по хешу (`ReplayedMessage`) — наш фильтр остаётся страховкой.
- **Replay/правки/ответы (CR-19)** — наш слой: `(session_id, message_index) → message_id` (индекс берём из
  шифротекста `MegolmMessage::message_index`), монотонный `edit_seq`, сверка `in_reply_to` с `replies`. В
  matrix-sdk-crypto проверки повтора Megolm нет — подтверждено.
- **Подпись запросов/ответов** — JSON-строки на границе FFI; ответы сервера разбираются
  `IncomingResponseExt::try_from_http_response` (как в `matrix-sdk-crypto-ffi`). ruma-типы наружу не торчат.
- **Тулчейн** — `rust-toolchain.toml` = 1.96.1 (MSRV 0.19.1 = 1.96).
- **Контракт v1** (JSON `/e2ee/*` в форме Matrix, конверт v1, payload v1, события WS) — черновик заморозки в
  `fixtures/` (сгенерирован прототипом). Отличия от плана, о которых должен знать бэкенд, — отчёт §5.

## Обязательные правила адаптера (выявлены спайком)

1. Подавать to_device по одному событию (иначе запрос ключа, пришедший в одной пачке с ключом, теряется).
2. После каждого прохода — `get_missing_sessions(∅)` (ответы на запросы ключей, залечивание Olm).
3. Держать в `tracked_users` себя и всех участников зашифрованных каналов (иначе запросы SAS игнорируются, а
   отправитель не связывается с устройством).
4. Не пересылать `sender_key` в конверт; `device_id` в конверте — подсказка, сверяется с
   `EncryptionInfo.sender_device` (несовпадение → `Mismatch`).
5. Сериализовать операции на один аккаунт (актор, CR-17) и держать файловый замок на хранилище — библиотека не
   защищает от второго экземпляра.

## Риски

| Риск | Мера |
| --- | --- |
| Частые несовместимые изменения API (0.16 → 0.19: `with_store` → `OlmMachineBuilder`, устаревший `import_backed_up_room_keys`, ruma 0.14 → 0.17) | Пин `=x.y.z`; обновление раз в квартал отдельным PR; табличные тесты адаптера + сценарии S1–S12 как регрессия; тест миграции хранилища на снимках каждой выпущенной версии (`fixtures/stores/`) |
| Изъян бэкапа v1 (сервер может подложить сессию) | Ключи из бэкапа всегда `Unauthenticated` в UI |
| Fallback ротируется по возрасту, а не по использованию | Сервер отдаёт использованный fallback повторно (BE-04), `device_unused_fallback_key_types` всегда в ответе |
| Размер бинарей | Запас по C23 большой (wasm 0,94 из 3 МБ gzip, `.so` 5,3 из 12 МБ), но в замере нет UniFFI/наших типов; шаг CI с порогом +5 % (CR-02) |
| Два экземпляра машины на одном хранилище | Файловый lock + один процесс (CR-17); в вебе — Web Locks (CR-14) |
| Без внешнего аудита (O8) | Внутреннее ревью адаптера/CR-19/FFI по чек-листу; меньше своего крипто-кода — меньше площадь ошибок |
| Тяжёлая сборка (LTO, ~250 крейтов) | Кэш реестра/target в CI; LTO только для релизных артефактов |

## Дополнения (блок 3B, 2026-10-18)

### A1. Таблицы CR-19: хранение и обрезка

Решение по открытому вопросу отчёта §6 («таблица replay — своя таблица или `custom_value`»): **`custom_value`
хранилища библиотеки**, своей SQLite-таблицы нет (второй файл/соединение, отдельная миграция и отдельная
реализация для IndexedDB не окупаются). Значения шифруются `StoreCipher`, как всё хранилище, и переживают рестарт.
Ключи (`crates/stoat-crypto/src/binding.rs`):

| Ключ | Что | Граница |
| --- | --- | --- |
| `stoat.seen.v1.<session_id>` | канал сессии + `message_index → message_id` | 1024 индекса на сессию (уходят младшие) |
| `stoat.seen.v1` | порядок появления сессий | 2048 сессий (уходят старейшие вместе с их записью) |
| `stoat.edits.v1.<channel>` | только правленые сообщения: `message_id → (edit_seq, session, index)` показанной версии | 512 на канал (уходят старейшие ULID) |

Сессии ротируются раз в 100 сообщений/неделю, поэтому запись сессии мала: расшифровка = одно чтение и одна запись
только при первом показе индекса. Цена границ: повтор (session, index) из вытесненной сессии и откат правки
вытесненного сообщения больше не помечаются. Первый увиденный устройством `message_id` для (session, index)
считается оригиналом — если сервер первой отдаст копию, помечен будет оригинал. Ключи блока 3A
(`stoat.replay.*`, `stoat.edit.*`) не мигрируются: сборки с ними не выпускались.

**Правки.** Правка в Stoat — `PATCH` на месте, id сообщения не меняется, поэтому `edit_of` обязан равняться id
сообщения, которое его несёт. `edit_mismatch` = (`edit_of` ≠ id) или поля несогласованы (`edit_of` без
`edit_seq ≥ 1` и наоборот). `stale_edit` — версия с `edit_seq` не выше уже показанной (кроме перерасшифровки той
же версии).
