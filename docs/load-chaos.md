# Нагрузка и хаос на стенде (этап 5, блок 5C-1)

Прогон 2026-10-18: `stoat-crypto` `main` (коммиты `b2a1395`…`9e2937f`), бэкенд `stoatchat` ветки
`durio/stage-2` (`5414a613`). Стенд — `scripts/testkit-backend.sh up`: debug-сборки delta, bonfire, autumn,
pushd в Docker (по 1 ГиБ на контейнер), MongoDB rs0, Redis 7, RabbitMQ 4, MinIO; второй сервер для T14
(свои mongo rs1, redis, rabbit, delta2, bonfire2). Машина разработчика, 16 ГиБ на Docker, 22 ядра. testkit —
тоже debug-сборка ядра (`cargo nextest`, профиль `test`).

**Все абсолютные числа ниже — debug и одна машина**: они нужны, чтобы видеть порядок величин и узкие места, а
не как бюджет для прода. Release-замер на VPS и на телефоне — отдельная задача (см. «До включения»).


## 1. T1–T19 на живом бэкенде

Все 19 сценариев плана (`docs/plan/00-architecture.md`, «Тест-сценарии») идут против живого бэкенда:
`tests/live.rs`, 16 тестов, все зелёные; `check` — «mongo: 18 channels, 2 files, ciphertext only; minio: no
plaintext objects». Таблица соответствия — в `docs/review-checklist.md` §6.

Как сделаны ранее не живые:

- **T11** (push): pushd работает на стенде без ключей FCM; тестовая очередь, привязанная к routing key
  `notifications.outbound.fcm` обменника `revolt.notifications` (management API RabbitMQ), получает
  `PayloadToService`: конверт, `body` «New message from <имя>», `user_id`/`session_id` получателя — текста нет;
  устройство получателя расшифровывает конверт из push после одного прохода ящика. Преобразование в FCM `data`
  (строки, `encrypted="1"`, предел 3,5 КиБ) покрыто юнит-тестами pushd (`consumers/outbound/encrypted.rs`).
- **T14**: тот же человек (почта, пароль) на двух бэкендах: разные учётки и устройства, `keys/query` одного
  сервера не знает устройств другого, токен одного сервера не принимается другим, сообщение одного сервера не
  расшифровывается ключами другого. Маршрутизация push по `instance`+`recipient` и раздельные хранилища — на
  стороне клиента (AN-06, AN-12), здесь не проверяются.
- **T8/T16/T17** — через настоящий API, а не подменой в памяти: тот же конверт под новым id (повтор),
  конверт ЛС в группе (перенос → `ChannelMismatch`), чужой конверт с подсказкой устройства своего (сервер
  отклоняет чужую подсказку 400; со своей — `SenderMismatch`/`Mismatch`), откат правки `PATCH`-ем старого
  конверта (`stale_edit`).
- **T13**: OTK вычерпаны друзьями (50 claim по одному), затем fallback; после расшифровки ядро догружает 50
  OTK. `matrix-sdk-crypto` 0.19.1 меняет fallback-ключ раз в неделю, а не после использования: он остаётся
  «использованным», и сервер обязан отдавать его снова — проверено вторым вычерпыванием в той же неделе.
- **T18**: маршрута снятия нет (404), другой алгоритм не принимается, открытый текст — 400; ядро хранит
  состояние канала у себя и после перезапуска шифрует без запроса к серверу. Предупреждение в UI — у хоста
  (AN-39, WEB-05).
- **T19**: устройство с SQLite обрабатывает страницу ящика, «падает» до `ack`, после перезапуска получает те же
  id: все отброшены до библиотеки (`skipped_duplicates = n`, `processed = 0`), у отправителя нет `m.dummy`.

## 2. Нагрузка

`load_group_fanout`, 50 пользователей по одному устройству, одна зашифрованная группа из всех 50. Фазы и время
(прогон после последнего коммита):

| Фаза | Время | to-device отправлено |
| --- | --- | --- |
| регистрация 50 (параллельно) | 6,6 с | — |
| открытие 50 устройств (машина, сокет, `keys/upload`) | 1,1 с | — |
| 49 заявок в друзья + группа + `set_channel_members` | 20,6 с (лимит `users` 20/окно: 38 × 429) | — |
| первая отправка: query 50, claim 49, 49 ключей комнаты | 0,67 с | 49 |
| все 50 забирают ключ и читают | 3,2 с (на устройство p50 3,1 с) | — |
| **всплеск**: 50 отправляют одновременно | 5,2 с (p50 5,1 с, max 5,2 с) | 2 401 |
| все разбирают по 49 ключей (pre-key Olm) | 13,7 с (p50 13,1 с) | — |
| 250 обычных отправок (по 5, Megolm) | 1,4 с (p50 117 мс, p95 976 мс) | 2 352 (повтор, см. L1) |
| каждый читает все 301 сообщение | 34,9 с (расшифровка p50 42 мс/сообщ., debug) | — |
| проверка OTK | 0,1 с: у всех 50 снова 50 | — |

Итог: 2 830 HTTP-вызовов, **0 ответов 5xx, 0 ошибок транспорта**, 38 × 429 (только заявки в друзья). 15 050 из
15 050 расшифровок чистые, `undecryptable = 0`, дублей ящика 0, «сдавшихся» устройств 0, отказов своих
запросов 0, грязных пользователей 0. Ящик: 4 802 сообщения обработано, ~176 to-device/с в фазе разбора
(debug-ядро: создание входящих Olm-сессий — основная цена).

Задержки маршрутов (p50 / p95 / max, мс): `POST /channels/{id}/messages` 97 / 126 / 878; `PUT
/e2ee/to_device/{txn}` 170 / 400 / 1 792; `GET /e2ee/to_device` 39 / 1 456 / 2 416; `POST /e2ee/to_device/ack`
200 / 688 / 2 048; `POST /e2ee/keys/query` 59 / 673 / 768; **`POST /e2ee/keys/claim` (49 устройств) 2 904 /
4 199 / 4 202**; `POST /e2ee/keys/upload` 74 / 290 / 671; `GET /e2ee/keys/count` 41 / 475 / 883; `GET
/channels/{id}/messages` 421 / 952 / 1 738. Память стенда после прогона: delta 137 МиБ, bonfire 35 МиБ, mongo
514 МиБ.

Наблюдения:

- **L1 — повторная раздача ключа комнаты.** В фазе обычных отправок 48 из 50 участников ещё раз разослали свой
  ключ всем (2 352 сообщения, та же сессия Megolm, ротации нет). Причина — поведение `matrix-sdk-crypto`: новая
  входящая Olm-сессия от устройства поднимает его `olm_wedging_index`, и библиотека пересылает исходящую
  сессию этому устройству при следующей отправке (`olm/account.rs:1420-1430`,
  `session_manager/group_sessions/mod.rs:753-760` в 0.19.1). Во всплеске каждая пара создаёт сессии в обе
  стороны. Цена — двойная раздача в первом «круге» новой активной группы; не ошибка, принимаем.
- **`keys/claim` медленный при параллельном всплеске**: 49 устройств за 3–4 с (`keys_claim.rs`,
  `CLAIM_CONCURRENCY = 8`, по одному `claim_one_time_key` на устройство). Раз на устройство-пару, дальше Olm
  переиспользуется; для группы 100 — кандидат на пакетный claim в BE, если release-замер подтвердит.
- Ящик стенда ограничен `max_pending_to_device = 64` (для Q11), в нагрузке до него не доходит (49 на устройство).

## 3. Хаос

`tests/chaos.rs`. Сценарий «во время потока»: группа A, B (2 устройства), C; A шлёт 12 сообщений (новый ключ
комнаты на каждом 4-м), B2 и C синхронизируются; в это время цель рестартует (Redis) или выключается на 5 с
(bonfire, delta). Потом клиенты восстанавливаются по правилам хоста (потерян сокет → reconnect +
`receive_reconnect` + проход ящика; иначе — проход ящика) и проверяется: каждое сообщение, которое **сервер
сохранил** (включая те, на которые клиент получил ошибку), расшифровывается чисто у всех трёх читателей.

| Сценарий | Простой | Ошибки у клиента | Сокеты | Восстановление | Сходимость |
| --- | --- | --- | --- | --- | --- |
| Redis restart | 1,8 с (данные Redis теряются) | 1 обрыв (паника ratelimiter, B2) | по-разному, см. B3 | 27–314 мс | 15/15, undecryptable 0, дублей 0 |
| bonfire stop 5 с | 8,9 с | 0 (HTTP жив) | все 4 потеряны | 86–250 мс | 14/14 |
| delta stop 5 с | 9,1 с | 3 обрыва, отправка повторена | живы, звонки идут | 24–293 мс | 16/16 |
| RabbitMQ restart | 9,2 с | 3 × 500 на отправку (B1) | — | после рестарта delta | 8 сохранено, 8 читаются |
| сокеты рвутся, ящик задом наперёд и дважды | — | — | 5 обрывов | — | 10/10; повтор страницы: 3 из 3 отброшены, разворот 3 Olm-сообщений одной сессии: 0 ошибок |
| delta stop 10 с + свой запрос (SAS) | 10 с | статус 0, не выброшен | — | 18–29 мс | SAS доведён до `Done`, `Verified` |

**O-2 под отказом:** за 10 с простоя delta запрос SAS (свой запрос ядра) ушёл 4 раза за 35 проходов
(пауза 0,5 → 1 → 2 → 4 с, `wakeup_in_ms` отсчитывает её), `rejected` пуст — статус 0 не постоянный отказ; после
старта delta запрос дошёл через 1,8 с, проверка завершилась. Повторы `ack`, ключей комнаты и запросов
библиотеки после рестартов ни разу не дали двойной обработки: `skipped_duplicates` 0 в серверных сценариях,
дубли — только там, где их подсовывали намеренно.

## 4. Ошибки бэкенда (не исправлены здесь, `stoatchat` не трогали)

**B1. После рестарта RabbitMQ сервисы не переподключаются к AMQP.** `AMQP` держит каналы, созданные один раз
(`crates/core/database/src/amqp/amqp.rs:28-36`), переподключения нет; pushd — одно `Connection`
(`crates/daemons/pushd/src/main.rs:37-50`), после `Connection reset by peer` процесс жив, но ничего не
потребляет.
- debug-сборка: `EventV1::p` паникует на `publish_event` (`crates/core/database/src/events/client.rs:446-452`,
  `panic!` под `cfg!(debug_assertions)`) → `message_send` отвечает 500, **хотя сообщение уже сохранено**;
- release: ошибка только в лог, но `AMQP::message_sent` (`tasks/ack.rs:176`) тоже мёртв → **ни одного push ни
  для кого**, пока не перезапустить delta и pushd.
- Повтор: `testkit-backend.sh chaos` (`chaos_rabbit_restart`) или вручную: `up`, `docker restart
  durio-test-rabbit`, отправить сообщение: 500 (debug); push в `notifications.outbound.fcm` не приходит, пока не
  перезапущены delta и pushd (проверено: после рестарта только delta — push нет; после pushd — есть).
- Для E2EE на Android это главное: push — единственный способ узнать о сообщении при закрытом приложении.

**B2. Первый вызов после рестарта Redis паникует.** `EventV1::p`: `redis_kiss::publish(...).await.unwrap()`
(`client.rs:444`) → `FailedConnection` → паника обработчика → 500 на уже сохранённое сообщение; лимитер:
`get_connection().await.expect("Failed to get redis connection")` (`crates/core/ratelimits/src/ratelimiter.rs:148-150`)
→ соединение рвётся. Не зависит от сборки. Хуже всего с идемпотентностью: повтор с тем же `nonce` получает 400
`InvalidOperation` (`messages/model.rs:298-301`, `consume_nonce`) — клиент не узнаёт id сохранённого
сообщения. Повтор: `chaos_redis_restart` (паника лимитера — в каждом из 6 прогонов, 500 → 400 на отправке — в
одном) или `docker restart durio-test-redis` и сразу отправка.

**B3. После рестарта Redis часть сокетов bonfire «молчит».** Подписчик сокета — `fred` с политикой
переподключения и `manage_subscriptions()` (`crates/bonfire/src/websocket.rs:245-258`), но в 2 из 6 прогонов
сокет B1 остался открытым и не получил больше ни одного события (в последнем — 30 с, 6 проб с новым ключом
комнаты), а новый сокет того же сеанса получает их сразу. В остальных прогонах bonfire закрыл сокет, клиент
переподключился — это нормальный путь. Клиент молчащий сокет не отличит (Ping отвечает bonfire сам).
Повтор: `CHAOS_FILTER='test(/^chaos_redis/)' scripts/testkit-backend.sh chaos`, в
`out/testkit/chaos/chaos_redis_restart.json` — `old_socket_rings_again_after_s = null` при
`sockets_lost[1] = false`.

**B4. Гонка upsert в `channel_unreads` теряет push целой пачки.** `tasks/ack.rs:149`:
`add_mention_to_unread(...).await?` — upsert по `_id.channel`/`_id.user` (`channel_unreads/ops/mongodb.rs:86-109`)
гоняется с другим upsert того же ещё не существующего документа (`acknowledge_message`, там же `:18-45`) →
duplicate key → `?` прерывает `ProcessMessage`: упоминания остальных пользователей **и все push пачки**
(`ack.rs:155-180`) теряются (`ERROR revolt_database::tasks::ack … update_one channel_unreads`). Ошибка upstream,
но правило E2EE «в ЛС/группе упомянуты все получатели» проводит через этот путь каждое зашифрованное сообщение.
Повтор: `testkit-backend.sh load` — 1 раз из 3 прогонов, первые сообщения после создания группы.

## 5. До включения `features.e2ee` в проде

1. **B1** — исправлено в `stoatchat` `durio/stage-5` (9bb9b3a1): AMQP переподключается при ошибке
   публикации (backoff 0,5–30 с), pushd следит за соединением и заново поднимает потребителей; событие
   больше не роняет запрос. В self-hosted всё равно `restart: unless-stopped`.
2. **B2** — исправлено (ce44f7c5): Redis в `EventV1::p` без паники (3 попытки, потом лог), лимитер
   fail-open без Redis, повтор `nonce`/`Idempotency-Key` того же автора в том же канале → 200 с уже
   сохранённым сообщением. 400 `InvalidOperation`/409 остаются для гонки с первым запросом и после
   рестарта delta — outbox клиента по-прежнему трактует их как «вероятно, отправлено» → перечитать канал.
3. **B3** — исправлено (2fbf9690, b223a7f9): bonfire закрывает сокет при любой ошибке/переподключении
   подписчика Redis (QUIT ограничен 2 с — он и вешал слушателя). Клиентам — переподключение + проход ящика;
   страховочный проход раз в минуту на переднем плане оставить.
4. **B4** — исправлено (580be38a): upsert повторяется при E11000, пачка не прерывается.

Повторный прогон на `durio/stage-5`: хаос (Redis ×7, RabbitMQ, bonfire, delta) и нагрузка 3/3 — без 5xx, паник
и ошибок сервисов. `push_delivered_pushd_not_restarted` в `chaos_rabbit_restart` остаётся `false` из-за
второго устройства bob в сети (`filter_online`); переподписка pushd проверена вручную.
5. Release-замер этой же нагрузки на VPS (Contabo) и расшифровки на телефоне: debug-числа здесь не бюджет;
   отдельно — `keys/claim` на 100 устройств.
6. На стенде `max_pending_to_device = 64`; в проде — значение по умолчанию (10 000).

Ядро и протокол: ошибок не найдено. Все расхождения выше — серверные; поведение ядра под отказами (повторы,
паузы, дубли, разворот, рестарты) соответствует контракту хоста.
